# Compile the WorkFlow core to a native binary with elephc

This is an **experimental build target**, not a replacement for the Composer
package, the [FrankenPHP JSON-RPC server](../README.md), or the
[TypePHP module](../typephp/README.md). Start with
[the PHP, Node, and Python guide](../../docs/languages.md) if you are choosing
how your application should connect.

[elephc](https://elephc.dev) compiles a static subset of PHP ahead of time to
native assembly: no VM, no Zend Engine, no opcode fallback. This module compiles
the same `src/` core and the same JSON protocol as the TypePHP module into:

- `workflow-native`: an executable that reads one JSON request from standard
  input and prints one JSON response.
- `libworkflow_native.{dylib,so}`: a C-ABI shared library, plus the
  `libworkflow_native.h` header **generated by the compiler**. The included
  Python example calls it in-process using `ctypes`, and
  [the C example](examples/c_host.c) links against the generated header.

Unlike TypePHP, elephc does not embed a PHP runtime. The artifacts for this core
need **no PHP, PHPX, GMP/MPFR, or `LD_LIBRARY_PATH`**: JSON, hashing, dates, and
arrays are compiled in. They are still platform-specific, and the Elephc runtime
library is part of the artifact.

> **Status.** This module is scaffolding that has not yet been built or run: the
> compiler is not installed in CI, and nothing here has been verified against a
> real `elephc` release. Treat the file layout and the host contract as reviewed
> design, not as a tested artifact. See the ADR
> [0007](../../docs/adr/0007-elephc-native-module.md) for the plan and the known
> risks.

## Build and test

elephc installs outside Composer. Install it once, then build from the
repository root:

```sh
curl -fsSL https://get.elephc.dev | sh
elvm install latest && elvm use latest --global
# macOS alternative: brew install illegalstudio/tap/elephc

sh mod/elephc/build.sh
```

`build.sh` runs `elephc --check` first (which also executes the cdylib
call-graph safety validator for exported code), then emits the executable and
the shared library into `build/` and the generated header into `include/`.

To exercise the artifacts end to end, generate the shared parity oracle with
PHP 8.3 and run the conformance and Node tests:

```sh
php mod/native/tests/export-cases.php build/php83-cases.json
WORKFLOW_NATIVE_BIN=mod/elephc/build/workflow-native \
WORKFLOW_NATIVE_LIB=mod/elephc/build/libworkflow_native.dylib \
WORKFLOW_ORACLE=build/php83-cases.json \
  python3 mod/elephc/tests/conformance.py
WORKFLOW_NATIVE_BIN=mod/elephc/build/workflow-native \
  node --test mod/elephc/tests/node_client.test.mjs
```

Or through the repository Makefile:

```sh
make elephc-build
```

`make elephc-test` runs the compiler check and build; it needs a PHP 8.3
interpreter for the oracle. Unlike `make native-test`, it does not use Docker and
can run directly on an Apple Silicon Mac.

Then try a complete approval flow from Python or C:

```sh
WORKFLOW_NATIVE_LIB=mod/elephc/build/libworkflow_native.dylib \
  python3 mod/elephc/examples/python_client.py
```

The result should contain `"status": "completed"` and
`"Approved from Python"`. Read [the example](examples/python_client.py) to see
how to initialize the library, start a run, request work, submit its outcome,
and release resources.

To call the executable instead (defaults to the host platform's library name
when run through the shipped examples):

```sh
printf '%s' '{"protocol":1,"operation":"start","run_id":"approval-1","definition":{"key":"approval","steps":[{"id":"approve"}]}}' | \
  mod/elephc/build/workflow-native
```

Check `ok` in the JSON response. Domain errors return `ok: false`, even when the
executable itself exits successfully.

## What the host must do

Every request contains `protocol: 1` and an `operation`:

| Operation | Input | Result |
| --- | --- | --- |
| `start` | `run_id`, `definition` | A new pinned run state; no work is executed |
| `evaluate` | `state` | Recalculated progress |
| `advance` | `state` | Updated state and newly issued `work` items |
| `complete` | `state`, `completion` | State after accepting a deferred result |
| `cancel` | `state` | Cancelled state; no further work is issued |

Success responses contain `ok`, `state`, and `work`. Each work item contains
`flow_key`, `run_id`, `step_id`, and `attempt`. A completion uses those four
fields plus `idempotency_key` and `result`. Result status is `completed`,
`failed`, or `skipped`; optional fields are `message`, `error`, `retriable`,
and `metadata`.

For example, a Python application can implement an `email` step using its own
mailer. WorkFlow only decides when that step becomes eligible:

1. Load the latest state and call `advance`.
2. Atomically save the returned state **and the work items to deliver** before
   performing external work. Use your own locking/version checks and outbox.
3. Perform the work using a stable idempotency key derived from its run and
   step (and, where appropriate, attempt).
4. Load the latest state, apply `complete`, and atomically save its result.
5. Call `advance` again to obtain newly eligible dependent steps.

The library is stateless: it does not remember previous calls, deduplicate
`start`, save data, queue jobs, schedule retry deadlines, or contact providers.
Reusing an old state can reissue work. An `advance` on the latest waiting state
returns no duplicate work; persist the original work items so a host crash does
not lose them. Cancellation stops future work but does not undo an operation the
host has already started. See [run lifecycle](../../docs/run-lifecycle.md).

Use only trusted definitions and persisted snapshots. This in-process interface
is not a security sandbox and provides no subject/tenant authorization. Keep
host credentials out of snapshots and ensure explicit result messages are safe
for their intended audience. Optional Laravel and Temporal adapters are not
included in these native artifacts; there is no foreign-language callback
interface for arbitrary PHP executors or state stores yet.

## C interface and runtime ownership

The compiler generates `libworkflow_native.h` from the `#[Export]` function in
[php/workflow_native.php](php/workflow_native.php); include it rather than
copying declarations. It contains the Elephc boundary API plus the resolved
export prototype:

```c
uint32_t    elephc_abi_version(void);
int32_t     elephc_init(void);
void        elephc_shutdown(void);
int32_t     elephc_last_status(void);
const char *elephc_last_error(void);
void        elephc_free(void *ptr);

/* Flattened string input, caller-owned string output. */
int32_t workflow_native_call(const char *request_ptr, size_t request_len,
                             char **output_ptr, size_t *output_len);
```

- **Initialize, call, and shut down on the same OS thread.** The elephc ABI is
  single-threaded and exposes no per-host runtime context; a host must not call
  the library concurrently. A Go binding would need a dedicated locked OS
  thread; Go/Rust bindings have not been implemented.
- `elephc_init()` then `elephc_shutdown()` around the process lifetime;
  shutdown is terminal. Reopening means a new process.
- Inputs are UTF-8 JSON. The protocol itself rejects a request over 1 MiB with
  `ok: false`; the boundary does not impose that limit for you.
- A successful call returns `ELEPHC_STATUS_OK` and an independently owned buffer
  whose trailing NUL is a convenience, not part of `output_len`. Release it with
  `elephc_free()` — never the caller's allocator. Domain errors keep the buffer
  and return `ok: false` JSON.
- A non-zero status is an ABI or runtime failure, not a workflow outcome; read
  `elephc_last_error()` for the diagnostic. A recovered failure leaves the host
  process running and the library usable.
- elephc rejects `exit`/`die` reachable from an export, so the compiler guarantees
  the library cannot terminate the host through an exit path. Hardware faults and
  memory corruption are still not contained; prefer the executable or RPC when
  process isolation matters.

## Why the protocol lives in `mod/native`

`mod/native/php/` holds the compiler-agnostic JSON front end
(`NativeFlow.php`, `api.php`, the stdin `main.php`, and the interpreter
oracle wiring) and `mod/native/tests/export-cases.php` holds the shared parity
fixtures. Both `mod/typephp` and `mod/elephc` compile that one copy, so the wire
contract and its tests cannot drift between the two compilers. The core flow
rules stay in `src/`; neither native module reimplements them in C++ or Python.

Only the elephc-specific parts live here: the `#[Export]` entry, the build
script, and the clients. TypePHP additionally needs `cpp/bridge.cc` and a
hand-written header because it embeds a PHP runtime; elephc needs neither.

## Known risks before this is verified

The ABI shape is not the risk — the export is a `string` in and a `string` out,
which is exactly the parameter set elephc marshals. The open questions are:

- **Static-subset compilation of `src/`.** The core uses no reflection, `eval`,
  variable variables, or generators, and relies on builtins elephc documents
  (`json_*`, `hash`, `date`, `array_*`, `bin2hex`, `iterator_to_array`). Expect
  the compiler to require explicit narrowing where a `mixed` value flows into a
  typed object parameter.
- **`random_bytes()`.** The core uses it once for a correlation ID, and it does
  not appear in elephc's builtin inventory; it may need a substitute.
- **Compile-time autoloading.** elephc resolves the `Webong\WorkFlow\` classes
  from Composer metadata rather than a runtime `spl_autoload_register` closure,
  so the build must run from the repository root.
- **No shared oracle run yet.** `mod/native/tests/export-cases.php` requires
  PHP 8.3, and CI does not install elephc, so parity is unproven.
